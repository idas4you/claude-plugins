# 구현

이 스킬은 `/idas4you-doc`이 쓰고 `/idas4you-doc-check`가 검수한 지시서를 구현한다. 지시서가 계약이다 — 지시서와 다르게 가야 하면 그 사실과 이유를 지시서에 적는다.

## 시작

1. 인자로 받은 지시서의 design.md·tasks.md(있으면 plan.md·관련 ADR)를 읽는다. 없으면 인덱스에서 찾고, 그래도 없으면 `/idas4you-doc`을 먼저 쓰라고 말한다.
   - **인자가 없으면 인덱스의 우선순위로 다음 지시서를 골라 제안한다.** 후보는 끝나지 않았고(`완료`·`중단`·`대체됨`이 아님) `선행 지시서`가 모두 `완료`인 것이다. 그중 우선순위가 가장 높은 것(상 → 중 → 하, 빈 칸은 `중`)을 고르고, 같으면 `진행 중`인 것, 그다음 오래된 것을 먼저 한다. "`<지시서>`(상 — 이유)부터 구현할까요?"라고 묻고, 나머지 후보를 순서대로 한 줄씩 보인다. 답을 받기 전에는 시작하지 않는다.
   - **인자로 받은 지시서의 `선행 지시서`가 끝나지 않았으면** 그렇다고 말하고, 그래도 진행할지 묻는다.
   - 인덱스의 우선순위는 읽기만 한다. 값을 바꾸는 것은 `/idas4you-doc`·`/idas4you-doc-check`와 사용자다.
2. 저장소 안내 파일(`CLAUDE.md`, `AGENTS.md`, 각 하위 레포의 안내)과 사용자 개인 안내를 읽어 다음을 정한다: 기능 브랜치 이름, 머지 대상 브랜치, 커밋 규칙·작성자, 시험 명령, 주석 언어.
3. 지시서에 미결 질문이 남아 있으면:
   - 지금 단계에 영향을 주면 구현 전에 묻는다.
   - 영향을 주지 않으면 그렇다고 밝히고 진행한다.
   - 답이 없으면 지시서의 권장안으로 가고, 그 가정을 결과 보고에 적는다.

## 구현 모델 — tasks.md의 `구현 모델 권장`을 따른다

이 스킬은 `opus`로 돈다(frontmatter). `/idas4you-doc-check`가 tasks.md 머리 표에 적은 `구현 모델 권장`이 그와 다르면, 그 단계의 구현을 **권장 모델의 하위 에이전트에 맡긴다**(Agent 도구의 `model`: `sonnet`·`opus`·`fable`).

| tasks.md | 하는 일 |
|---|---|
| 권장 줄이 없다 | 이 세션(`opus`)이 직접 구현한다. 보고에 "검수 없음 — `/idas4you-doc-check`를 거치지 않았다"고 한 줄 적는다 |
| 권장이 `opus` | 이 세션이 직접 구현한다 |
| 권장이 `sonnet`·`fable` | 그 모델의 하위 에이전트에 맡긴다 |
| 단계별 권장(예: P1 `sonnet`, P2~P3 `fable`) | 단계마다 따른다. `opus` 단계는 직접, 나머지는 단계별로 맡긴다 |
| 사용자가 이번 호출에서 모델을 말했다 | 사용자 말이 권장보다 먼저다 |

맡길 때의 규칙:

- **맡기는 것은 코드 구현과 단위 테스트까지다.** 브랜치 만들기, 전체 스위트 전후 비교, 실환경 측정, 지시서 기록, (사용자가 승인한 뒤의) 머지·push는 이 세션이 한다.
- 하위 에이전트는 이 대화를 모른다. 지시문에 다음을 넣는다: 지시서 파일의 절대 경로(직접 읽게 한다 — 요약해서 넘기지 않는다), 맡는 단계, 작업할 레포 경로와 이미 만들어 둔 기능 브랜치 이름, 읽어야 할 안내 파일, 아래 "구현" 절의 규칙(주석·범위·비밀값), 커밋 규칙과 작성자, 하지 말 것(머지·push·배포·지시서 완료 처리), 돌려줄 것(바꾼 파일·커밋 해시·돌린 테스트 명령과 결과·지시서와 다르게 한 것).
- 같은 레포를 건드리는 단계는 차례로 맡긴다. 서로 다른 레포의 독립 단계만 동시에 맡긴다.
- **돌아온 결과는 그대로 믿지 않는다.** diff를 읽어 지시서와 대조하고 테스트를 이 세션에서 다시 돌린다. 어긋나면 같은 에이전트에 이어서 고치게 하거나 직접 고친다.
- 하위 에이전트가 "지시서가 틀렸다"고 보고하면 이 세션이 코드로 확인한 뒤 지시서를 고친다.
- 결과 보고에 단계별로 어느 모델이 구현했는지 적는다.

### 고쳐도 통과하지 못하면 한 단계 위 모델로

같은 단계에서 **고치기를 두 번 했는데도** 지시서 대조나 테스트를 통과하지 못하면, 세 번째는 같은 모델에 다시 시키지 않고 한 단계 위로 올린다. 순서는 `sonnet` → `opus`(이 세션이 직접) → `fable`(하위 에이전트).

- 이 세션(`opus`)이 직접 구현하던 단계도 같다 — 두 번 고쳐도 안 되면 `fable` 하위 에이전트에 맡긴다.
- 올리기 전에 원인이 모델이 아니라 **맥락 부족**(지시문에 빠진 파일·규칙)이나 **지시서 오류**인지 먼저 본다. 그쪽이면 모델을 올리지 않고 지시문이나 지시서를 고친다.
- 올려 맡길 때는 새 에이전트에 지금까지의 시도와 실패 내용(실패한 테스트·출력, 어긋난 지시서 자리)을 함께 넘긴다.
- `fable`에서도 두 번 고쳐 안 되면 더 돌리지 않고 멈춰 사용자에게 보고한다.
- 올린 사실과 이유를 결과 보고와 tasks.md의 `구현 모델 권장` 줄 옆에 적는다(다음 검수의 추천 근거가 된다).

## 구현

- 추적 브랜치를 최신으로 받은 뒤 기능 브랜치를 만든다. 여러 레포에 걸치면 같은 이름.
- **원본을 먼저 찾는다.** 지시서가 "옮긴다·고정한다"고 한 스크립트·설정은 이전 세션 자료·저장소 이력에서 찾아 그대로 옮기고, 다르게 쓴 부분만 이유를 적는다.
- **지시서가 틀렸으면 코드를 지시서에 맞추지 말고 지시서를 고친다.** 실제 코드·데이터와 다른 표·수치·가정을 찾으면 design.md에 정정과 이유를 남긴다.
- 요청한 동작 하나만 넣는다. 부수 보호 장치는 제안만 한다.
- 작업하는 함수에는 저장소 관행대로 주석(무엇·왜)을 단다.
- 비밀값은 파일에서만 읽는다. 코드·로그·커밋에 넣지 않는다.

## 시험

- 단위 테스트 + 전체 스위트를 **변경 전후 실패 목록으로 비교**한다. 원래 실패하던 것과 새로 실패한 것을 나눈다.
- 분석 도구·스크립트를 만들었으면 **이미 결과가 알려진 원자료로 다시 계산해** 보고서 숫자와 맞는지 확인한다.
- 외부에 닿는 스크립트는 로컬 가짜 서버로 흐름을 먼저 돌린다(호스트 프록시 변수가 로컬 요청을 가로채지 않게 주의).
- 지시서에 실환경 측정이 있고 사용자가 그렇게 해 왔다면 **직접 돌린다.** 명령 목록만 넘기고 멈추지 않는다. 오래 걸리면 백그라운드로 돌리고 끝나면 이어 간다.
- 시험 산출물(`__pycache__`, 캐시, 임시 파일)이 커밋에 섞이지 않게 확인한다.

## 기록

- tasks.md 체크리스트와 검증 표를 그때그때 채운다(명령·결과·일자). 숫자는 실제 출력에서 옮긴다.
- 측정이 끝나면 저장소 관행대로 보고서를 쓰고 인덱스를 갱신한다.
- 지시서와 달라진 것은 design.md 수정 이력에 남긴다.

## 마무리

- 통과해도 **머지하지 않고 묻는다.** 기능 브랜치는 그대로 두고, 어느 브랜치에 머지할지 사용자에게 묻는다(안내 파일에 머지 대상이 있으면 그것을 권장안으로 댄다). 머지·push와 기능 브랜치 삭제는 사용자가 그러라고 한 뒤에 한다.
- 결과 보고: 무엇을 했고, 무엇을 확인했고(숫자), 지시서와 무엇이 달랐고, 남은 것이 무엇인지.

## 하지 않는 일

- 배포는 사용자가 명시적으로 요청할 때만.
- 머지는 어느 브랜치든 사용자가 그러라고 할 때만. 지시서 완료 처리는 사용자가 완료라고 할 때만.
- 사용자 작업을 끊는 정리(운영 파드 삭제 등)는 하지 않고 기록만 한다.
- 확인용 로그는 확인이 끝나면 지운다(지표로 남길 로그는 지시서에 그렇게 적힌 것만).
